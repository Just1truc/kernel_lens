KernelLens compiles a PyTorch module with custom @triton.jit kernels into native ONNX Runtime and TensorRT C++ plugins. The engine folds your standard layers; your kernels stay kernels for the operations folding cannot express.

What it is

One call, two artifacts, two engines.

Compile

kl.compile(model, sample_input) traces the module, rewrites it into an ONNX graph with injected custom nodes, synthesizes the C++ plugin classes and builds the shared libraries. You keep writing Triton in Python.

Run

compiled_model.run(inputs, backend="tensorrt") executes in the engine with zero-copy VRAM binding — PyTorch's data_ptr() handed straight to the engine, no host staging.

Fold + keep

The engine folds your standard layers; your kernels run as native plugins for the operations folding cannot express. You get both in one C++ graph.

The problem

Production runs in C++. Your Triton kernels do not.

Enterprise inference is served by pure C++ engines — ONNX Runtime and TensorRT — for latency, concurrency and whole-graph optimisation. But torch.onnx.export traces TorchScript or TorchDynamo IR that represents native PyTorch operators; an imperative Python call to a triton.JITFunction is opaque to it. The kernel is dropped or the export fails.

Doing it by hand means re-implementing the kernel in CUDA, writing the ONNX and TensorRT plugin classes, patching the PyTorch graph, and building and loading the result. A Triton kernel is not one operator — it presents five properties a C++ engine must recover.

GapWhy it breaks a naive export
PTX entry ABITriton's PTX re-orders, drops and re-bitwidths parameters; the host must rebuild the exact slot layout.
Dynamic launch gridThe grid is a Python expression over runtime shapes, e.g. (s0*s1+127)//128; it cannot be frozen at compile time.
Nested & in-place codeStores delegated to helpers and buffers mutated in place produce spurious copies or corrupted graphs.
Dynamic host scalarsPer-call values (a soft-cap τ, a scale α) must be accepted without recompiling the engine.
Quantized layoutFP8 and sub-byte INT4 need 1-byte pointer mapping and dtype-accurate memory placement.
How it works

What you would build by hand — and what KernelLens does instead.

To put one Triton kernel into either engine manually, you port it to CUDA, implement the ONNX classes (Ort::CustomOp, Ort::CustomOpApi, domain registration), implement the TensorRT classes (nvinfer1::IPluginV2DynamicExt, nvinfer1::IPluginCreator), write a CMake build, patch the FX graph with a C++ extension and @torch.library.custom_op, export, build the engine, and then drive each engine yourself — creating the session, binding raw CUDA pointers, creating the execution context, calling setTensorAddress and enqueueing.

The compile pipeline

kl.compile(model, sample_input, backends=[...]) produces a validated manifest, an ONNX graph and the plugin libraries. Each arrow below is a concrete artifact.

Trace

Recover what the kernel really is

  • An eager pass intercepts the compiled PTX, shared memory, warps, the real grid and every argument's shape and strides.
  • A symbolic pass recovers the launch grid as an expression over runtime shapes.
  • A static AST scan of tl.load/tl.store classifies each argument as input, output or in-place.
Rewrite

Inject custom nodes

  • Inside torch.onnx.export, Triton calls become triton_custom::<kernel> nodes carrying the PTX.
  • Per-call scalars become CPU inputs, so a new value needs no recompilation.
  • In-place buffers are wired input-to-output so the optimiser sees the mutation.
Synthesize

Generate the C++ classes

  • An OrtCustomOp class for ONNX Runtime.
  • An IPluginV2DynamicExt + IPluginCreator for TensorRT.
  • The PTX entry-slot argument array is rebuilt and the grid is evaluated in C++.
Build

Compile and harden

  • nvcc + g++ produce the shared libraries.
  • PTX ISA versions are clamped for older driver JITs; conda CUDA header layouts are resolved.
  • A 16-byte alignment guard stages sub-aligned tensor slices through an aligned buffer.

The run pipeline

At run time, PyTorch's GPU addresses are handed straight to the engine.

import torch, triton, triton.language as tl
import kernel_lens as kl

class RMSNorm(torch.nn.Module):
    def forward(self, x):
        B, M, N = x.shape
        out = torch.empty_like(x)
        rmsnorm_kernel[(B, M)](x, self.weight, out, x.stride(0), x.stride(1),
                               out.stride(0), out.stride(1),
                               N=N, eps=1e-6, BLOCK_SIZE=triton.next_power_of_2(N))
        return out

x = torch.randn(4, 512, 4096, device="cuda")
compiled = kl.compile(RMSNorm().cuda(), (x,), name="llama3_rmsnorm",
                      backends=["onnx", "tensorrt"])   # compile once

out_ort = compiled.run((x,), backend="onnx")            # run in ONNX Runtime
out_trt = compiled.run((x,), backend="tensorrt")        # run in TensorRT

Folding + kernels vs the alternatives

Same block, three ways to run it. A. Folded only expresses the attention with standard operators and lets the compiler fold everything (what you get if you cannot ship the kernel). B. Kernels only runs the custom kernels with the standard layers unfused (the usual way to use a Triton kernel) — in its torch.compile form the kernel is captured, not reimplemented: since PyTorch 2.1 TorchDynamo records a @triton.jit launch as a triton_kernel_wrapper_mutation node with no graph break, and Inductor emits a call to your kernel while fusing only the surrounding operators. Single-operator latency

The C++ plugin runs the same kernel behind an operator boundary, within 6–13% of native Triton on the three larger operators. The value is deployment, not raw speed on a single op.

End-to-end 4-layer LLaMA decoder

The TensorRT plugin nearly halves time-to-first-token (4.14 ms vs 7.85/7.92 ms) and attains the lowest peak VRAM, with total generation on par with the baselines.

Coverage: module patterns

Parity on specific operators is not enough — the compiler has to handle the many ways a module can call a kernel. A conformance suite (tests/test_conformance.py) exercises fourteen patterns against both backends; all pass at 0.00e+00.

Graph shapes
  • Two kernels in one graph
  • The same kernel launched twice — its own ONNX op and plugin per launch
  • Multiple outputs, including different shapes
  • Kernels inside a Python loop and behind a conditional
  • Kernels delegating to nested @triton.jit helpers
  • A 3-D launch grid
Data
  • Dynamic host scalars
  • Strided / non-contiguous inputs
  • Dynamic batch sizes
  • In-place mutation of an input buffer
  • fp16 and bf16
  • Boundary: ONNX Runtime 1.30 cannot bind bf16 to a custom op, so bf16 models use TensorRT, which handles them exactly.

TensorRT is fastest at every size and precision; in fp32 the margin grows with the model (3.6× to 5.6×), because the gain comes from the engine's graph optimisation around the plugin rather than the kernel itself. ONNX Runtime is competitive in fp32 but loses in fp16, where its compiled graph carries 1,583 nodes against 25 custom operators and per-node dispatch dominates. Accuracy tracks precision, not speed: fp32 keeps the same greedy token on ≥98.8% of positions, fp16 under TensorRT on 93.6–97.9%; OPT-350M in fp16 under ORT is bit-exact.

Why an engine

TensorRT is not always faster. Here is when it is.

torch.compile is a strong baseline — it fuses, and since PyTorch 2.1 it captures your Triton kernels rather than breaking on them (verified: zero graph breaks). So the honest answer to "why an engine at all?" is not "raw speed". Here is the head-to-head, on the same RTX 5060 Ti, with the custom kernels captured on both sides.

Configurationtorch.compileKernelLens TRTWinner
LLaMA decoder prefill (S=512)7.92 ms4.14 msTRT 1.9×
Conv model + custom kernel (fp32)10.40 ms11.40 mscompile 1.10×
Conv model + custom kernel (fp16)4.45 ms8.20 mscompile 1.84×
Transformer block (fp32)7.55 ms7.63 mstie

TensorRT wins on GEMM-heavy transformer prefill, where its kernels and folding beat Inductor's generated GEMMs. On convolution-heavy graphs it is still behind, even after two fixes: the plugin now declares channel-last formats for pointwise kernels (so the engine no longer inserts reformats around it), and it now enforces the dtype the kernel was compiled for (previously the engine silently ran fp16 models in fp32). Together these took the fp16 conv case from 10.86 to 8.20 ms with exact parity; the remaining gap is the engine's convolution performance, not the plugin.

Why an engine wins

Structural, not just numerical

  • No Python interpreter and no libtorch in the serving path — no GIL, a small footprint, deployable from C++, Rust, Go or Java services.
  • A serialized engine that cold-starts without recompiling.
  • Engine-level VRAM planning: 464 MB peak versus 473/478 MB in our decoder.
  • Dynamic shapes handled by optimization profiles rather than recompiles and guards.
  • Quantized inference (INT8/FP8 with calibration), where TensorRT is mature.
Why the kernel wins

Folding cannot express everything

  • If you cannot ship the kernel, the folded-only formulation is 2× slower — it must materialise the O(N²) attention.
  • The engine folds the standard layers around your kernel; the unfused path cannot.
  • Custom kernels stay kernels for exactly the operations folding cannot express efficiently.

Questions

Fair objections.

Does KernelLens make my kernel faster than Triton?

It runs the identical kernel behind a C++ operator boundary, so a single operator is within 6–13% of native Triton. The win is the combination: the engine folds the standard layers around your kernel, which the unfused path cannot, and the folded-only path cannot express the kernel at all. On a two-layer block that is 1.99× versus folded-only and 1.08× versus the unfused kernel path.

Then why use it?

Because production serves C++ engines. KernelLens lets a custom Triton kernel live inside TensorRT or ONNX Runtime, where the standard layers are folded and tuned, and the memory planner covers everything — and it removes the hand-written plugin.

Is the parity exact?

Against native Triton, yes: 0.00e+00 across the research kernels, the edge cases and the quantized GEMMs, on both backends.

Which hardware?

Everything reported here was measured on a single RTX 5060 Ti (sm_120a). KernelLens targets CUDA C++ engines on NVIDIA hardware; other GPUs, clusters and vendors are not extrapolated.
