\begin{abstract}
Custom GPU kernels written in OpenAI Triton \cite{triton2019} are now common in
deep-learning research, but deploying them is not. Production inference is
served by pure C++ engines---Microsoft ONNX Runtime (ORT) \cite{onnxruntime} and
NVIDIA TensorRT (TRT) \cite{tensorrt}---which apply whole-graph optimisation,
engine tuning and VRAM planning. A model that calls a \texttt{@triton.jit}
kernel does not fit that pipeline: the exporter cannot trace the kernel, and
reproducing what the engine needs by hand is a long, specialised build.

We present \textbf{KernelLens}, a compiler and runtime that reduces that build to
one call. \texttt{kl.compile(model, sample\_input)} traces the model, rewrites it
into an ONNX graph with injected custom nodes, synthesises the ONNX Runtime and
TensorRT C++ plugin classes, and builds the shared libraries; \texttt{run}
executes the result in either engine with zero-copy VRAM binding. We describe
the manual pipeline KernelLens replaces, then the compile and run pipelines in
detail.

The central empirical result is that KernelLens lets an engine \emph{fold} the
standard layers while a custom Triton kernel keeps the operations that folding
cannot express well. On a block whose attention is a custom squared-ReLU flash
kernel, KernelLens runs it in $7.63$~ms, against $15.15$~ms for the folded-only
formulation and $28.04$~ms for eager folding ($1.99\times$ and $3.68\times$
faster), and $1.08\times$ faster than the unfused Triton-kernel path---all
measured on an RTX 5060~Ti. The four research kernels reproduce native Triton
exactly inside ONNX Runtime.
\end{abstract}

\section{Introduction}

Deep-learning systems rely on fused GPU kernels for attention, normalisation and
activation blocks, reducing VRAM traffic and launch overhead. Triton has become
the standard way to author such kernels in Python. A friction point appears at
deployment: enterprise inference runs inside C++ engines---ONNX Runtime and
TensorRT---for latency, stream concurrency, hardware-specific kernel selection
and global memory planning, and a PyTorch model that calls a
\texttt{@triton.jit} kernel does not fit that pipeline.

The difficulty is not that the kernel is hard to compile. It is that the engine
consumes a graph plus a compiled plugin, and producing that pair by hand means
porting the kernel to CUDA, implementing the ONNX and TensorRT plugin classes,
patching the PyTorch graph, building the libraries, and driving each engine
yourself. Figure~\ref{fig:manual} lays that pipeline out next to KernelLens.

\begin{figure}[h!]
\centering
\includegraphics[width=\textwidth]{architectural_diagram.png}
\caption{Top: the manual pipeline. Every box is a class, a build step or an
engine call that must be written and maintained by hand --- from rewriting the
Triton kernel in CUDA, through \texttt{Ort::CustomOp},
\texttt{Ort::CustomOpApi}, domain registration,
\texttt{IPluginV2DynamicExt} and \texttt{IPluginCreator}, CMake, FX-graph
patching with \texttt{@torch.library.custom\_op}, ONNX export and TensorRT
engine building, to \texttt{RunWithBindings} and \texttt{Enqueue Execution}.
Bottom: KernelLens --- one compile call and one run call per backend.}
\label{fig:manual}
\end{figure}

KernelLens keeps the whole-graph wins \emph{and} the custom kernel. The engine
folds the standard layers; the Triton kernel stays a native plugin for the
operations that folding cannot express efficiently. We show this pays off:
on a block with a custom squared-ReLU flash attention, KernelLens is
$1.99\times$ faster than the folded-only formulation and $1.08\times$ faster
than running the kernels unfused (\S\ref{sec:eval}).

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=1.6em]
    \item A \textbf{compile pipeline} that turns an unmodified PyTorch module
    into an ONNX graph with injected custom nodes plus ONNX Runtime and TensorRT
    plugin libraries, recovering the compiled PTX, the dynamic launch grid and a
    per-argument input/output/in-place taxonomy (\S\ref{sec:compile}).
    \item A \textbf{run pipeline} that binds PyTorch GPU addresses directly to
    both engines with no host staging (\S\ref{sec:run}).
    \item An \textbf{empirical study} showing that folding the standard layers
    while keeping custom kernels is faster than either alone, plus parity,
    latency, end-to-end and quantized results (\S\ref{sec:eval}).
\end{enumerate}

\section{Background and Related Work}

\paragraph{PyTorch compilers.} \texttt{torch.compile}, powered by TorchInductor
\cite{pytorch20}, generates Triton for eager PyTorch graphs and is the natural
baseline. It optimises inside a Python process and depends on \texttt{libtorch};
it does not emit a standalone ONNX graph or a C++ plugin for a non-Python
server. AOTInductor \cite{aotinductor} compiles graphs to shared libraries but
still links against PyTorch's C++ tensor library.

\paragraph{Enterprise runtimes.} ONNX Runtime \cite{onnxruntime} and TensorRT
\cite{tensorrt} expose C++ custom-operator APIs (\texttt{OrtCustomOp},
\texttt{IPluginV2DynamicExt}) into which KernelLens synthesises code.

\paragraph{Triton kernel libraries.} Liger-Kernel \cite{ligerkernel},
FlashAttention \cite{flashattn1,flashattn2} and AOTriton supply high-quality
kernels. KernelLens is the deployment layer beneath them.

\paragraph{Positioning.} Table~\ref{tab:comparison} contrasts KernelLens with
adjacent tooling. The distinguishing property is the combination of automated
PyTorch graph export \emph{and} self-contained C++ plugins for both engines.

\section{What a Triton Kernel Presents to a C++ Engine}
\label{sec:anatomy}

A \texttt{@triton.jit} kernel is not one opaque operator; its launch site encodes
seven kinds of information, each of which reaches C++ through a different
mechanism (Figure~\ref{fig:anatomy}).

\begin{figure}[h!]
\centering
\includegraphics[width=\textwidth]{kernel_anatomy.png}
\caption{A Triton kernel decomposes into seven parameter categories. Each maps to
a distinct mechanism in the generated C++ plugin; the re-ordered PTX entry ABI
and the dynamic grid are why a naive exporter fails.}
\label{fig:anatomy}
\end{figure}

Formally,
\begin{equation}
\mathcal{K}_{\text{triton}} = \big\langle \mathbf{P}_{\text{in}},
\mathbf{P}_{\text{out}}, \mathbf{P}_{\text{inplace}}, \mathbf{S}, \mathbf{D},
\mathbf{C}, \mathbf{G} \big\rangle,
\end{equation}
where $\mathbf{P}_{\text{in}}$, $\mathbf{P}_{\text{out}}$ and
$\mathbf{P}_{\text{inplace}}$ are read-only, write-only and read--write VRAM
pointers; $\mathbf{S}$ are element strides; $\mathbf{D}$ are dynamic host
scalars; $\mathbf{C}$ are \texttt{tl.constexpr} values baked into PTX; and
$\mathbf{G}$ is the launch grid, computed from runtime dimensions and block
sizes.

\begin{table}[h!]
\centering
\small
\begin{tabularx}{\textwidth}{l l X}
\toprule
\textbf{Category} & \textbf{Meaning} & \textbf{Mechanism in C++} \\ \midrule
$\mathbf{P}_{\text{in}}$ & read-only pointers & plugin inputs, bound by address \\
$\mathbf{P}_{\text{out}}$ & write-only pointers & plugin outputs, engine-allocated \\
$\mathbf{P}_{\text{inplace}}$ & read and written & input/output aliasing \\
$\mathbf{S}$ & element strides & \texttt{int64} runtime arguments \\
$\mathbf{D}$ & per-call scalars & \texttt{OrtMemTypeCPUInput} / plugin member \\
$\mathbf{C}$ & \texttt{tl.constexpr} & baked in PTX, removed from ABI \\
$\mathbf{G}$ & launch grid & C++ integer expression evaluated at run time \\
\bottomrule
\end{tabularx}
\caption{Parameter taxonomy and the corresponding plugin mechanism.}
\label{tab:taxonomy}
\end{table}

Two consequences drive the design. Because PTX re-orders and drops parameters,
the host ABI must be \emph{reconstructed}. Because the grid is an arbitrary
expression over runtime shapes, it must be \emph{transpiled} and evaluated in
C++.

\section{The Manual Pipeline}
\label{sec:manual}

Before describing what KernelLens does, it is worth being concrete about what it
replaces. Figure~\ref{fig:manual} (top) is the pipeline a developer must build to
put one Triton kernel into either engine by hand. It splits into a compile side
and two run lanes.

\paragraph{Compile: port the kernel.} Rewrite each \texttt{@triton.jit} kernel as
CUDA C++, matching the numerics of the original.

\paragraph{Compile: implement the ONNX classes.} Derive from
\texttt{OrtCustomOp}, use \texttt{Ort::CustomOpApi} to read inputs, write outputs
and launch, and register a custom schema and domain so the graph parser accepts
the node.

\paragraph{Compile: implement the TensorRT classes.} Derive from
\texttt{nvinfer1::IPluginV2DynamicExt}, implement \texttt{getOutputDimensions},
\texttt{supportsFormatCombination}, \texttt{enqueue} and serialization, and
provide an \texttt{nvinfer1::IPluginCreator} plus registration.

\paragraph{Compile: build the libraries.} Author CMakeLists (or equivalent),
drive \texttt{nvcc} and \texttt{g++}, resolve the ORT and TensorRT headers, and
produce the shared library.

\paragraph{Compile: patch the graph.} Extend the PyTorch FX graph through a C++
extension, wrap each kernel with \texttt{@torch.library.custom\_op}, and inject
the custom nodes before export.

\paragraph{Output.} The pipeline yields three artifacts: the dynamic shared
library, an ONNX file, and a TensorRT engine file.

\paragraph{Run in ONNX Runtime.} Create an \texttt{Ort::Session}, load the
library, bind raw CUDA pointers through \texttt{Ort::Binding}, and call
\texttt{RunWithBindings}.

\paragraph{Run in TensorRT.} Load and deserialize the engine into an
\texttt{IExecutionContext}, call
\texttt{IExecutionContext::setTensorAddress} for every tensor, and enqueue the
execution.

Each step is a place where the ABI, the launch geometry, the memory placement or
the numerics can diverge from the original kernel. KernelLens performs all of
them from the unmodified module.

\section{The KernelLens Compile Pipeline}
\label{sec:compile}

\texttt{kl.compile(model, sample\_input, backends=[...])} produces a validated
manifest, an ONNX graph and the plugin libraries (Figure~\ref{fig:pipeline}).
The steps below are the internals of that single call.

\subsection{Tracing and manifest assembly}

KernelLens observes the model twice and inspects the kernel source once.

\begin{itemize}[leftmargin=1.5em]
    \item \emph{Eager pass.} The model runs normally on the GPU while
    \texttt{triton.JITFunction.run} is patched. For each launch it captures the
    compiled PTX, the dynamic shared-memory size, \texttt{num\_warps}, the real
    grid and every argument's shape, strides and dtype. This is the only pass
    that sees the true compiled artifact.
    \item \emph{Symbolic pass.} The module is re-executed under
    \texttt{make\_fx(tracing\_mode="symbolic")} with fake tensors, so the grid
    lambda evaluates over \texttt{SymInt} sizes and is captured as a symbolic
    expression for later transpilation. If this pass diverges from the eager
    pass, the concrete manifests are used unchanged.
    \item \emph{Static AST scan.} An \texttt{ast.NodeVisitor} walks the kernel
    source---recursively into Triton helpers---and records every
    \texttt{tl.load} and \texttt{tl.store} target. An argument in both sets is
    \texttt{inplace}; only stored is \texttt{output}; the rest are
    \texttt{input}.
\end{itemize}

The result is a \texttt{KernelManifest} carrying \texttt{ptx},
\texttt{shared\_memory\_bytes}, \texttt{num\_warps}, the argument taxonomy and the
transpiled grid expressions.

\subsection{Graph rewriting and node injection}

Phase two produces a standard ONNX graph. A hook runs inside
\texttt{torch.onnx.export} (opset 17): when a Triton kernel launches, the call is
diverted into a custom-domain node \texttt{triton\_custom::<kernel>} carrying the
PTX payload, the shared-memory size and the argument taxonomy. Two details matter
for correctness: per-call scalars are registered as CPU inputs
(\texttt{OrtMemTypeCPUInput}) so a new value needs no recompilation, and
in-place buffers are wired input-to-output so downstream optimisations see the
mutation. A short cleanup pass removes \texttt{Expand}/\texttt{Reshape} nodes
left between an injected node and its consumers.

\subsection{ONNX Runtime plugin synthesis}

For each kernel the ONNX generator emits a class deriving from
\texttt{OrtCustomOp}. It declares the input and output element types, marks
scalar inputs as CPU inputs, and in \texttt{Compute} reconstructs the launch
argument array and calls \texttt{cuLaunchKernel}. Arguments are read from the ORT
tensor API and passed as raw device pointers, so no data is copied.

\subsection{TensorRT plugin synthesis}

The TensorRT generator emits a class deriving from
\texttt{nvinfer1::IPluginV2DynamicExt} plus an \texttt{IPluginCreator} and a
registrar. It implements \texttt{getOutputDimensions} from the captured shapes,
\texttt{supportsFormatCombination} for linear formats,
\texttt{getOutputDataType}, serialization, and \texttt{enqueue}, where the grid
expression is evaluated in C++ over the runtime dimensions and the entry-slot
argument array is rebuilt to match the PTX.

\subsection{Compilation, hardening and engine building}

The generator writes the sources and invokes \texttt{nvcc} and \texttt{g++} to
produce the ONNX Runtime and TensorRT plugin libraries. Two pieces of hardening
make this portable: the PTX ISA version is clamped on load failure (a
Triton-generated \texttt{.version 9.3} becomes \texttt{.version 9.0}, then
\texttt{.target sm\_90}, so an older driver JIT can load Blackwell-targeted
PTX), and the build resolves conda CUDA header layouts. Generated plugins also
carry a 16-byte alignment guard: if a pointer is sub-aligned, the tensor is
staged through an aligned buffer before the launch, which avoids misaligned
vector-load faults on tensor slices. The TensorRT engine is built lazily on the
first run and cached.

\section{The KernelLens Run Pipeline}
\label{sec:run}

\texttt{compiled\_model.run(inputs, backend=...)} loads the shared library and
hands PyTorch's GPU addresses straight to the engine
(Figure~\ref{fig:zerocopy}).

\begin{figure}[h!]
\centering
\includegraphics[width=0.95\textwidth]{zero_copy_binding.png}
\caption{Zero-copy binding for both engines. Only pointer registration is
host-side; no tensor data crosses the PCIe bus.}
\label{fig:zerocopy}
\end{figure}

\paragraph{ONNX Runtime.} The runtime creates the \texttt{InferenceSession} with
the plugin library registered, then, per call, binds inputs and pre-allocated
outputs by CUDA device pointer through \texttt{IOBinding} and calls
\texttt{run\_with\_iobinding}. The session, the binding and the output tensors are
created once and reused, which removes most of the per-call host overhead.

\paragraph{TensorRT.} The engine is deserialised once into an
\texttt{IExecutionContext}. Per call, KernelLens sets the input shapes, registers
every tensor address with \texttt{set\_tensor\_address}, and issues
\texttt{execute\_async\_v3} on the current CUDA stream.

Both paths cost $O(1)$ pointer registration plus the kernel, versus $O(N)$ host
staging copies for a design that moves data through the CPU.

\section{Evaluation}
\label{sec:eval}

\subsection{Setup}

All measurements are on a single NVIDIA GeForce RTX 5060~Ti (16~GB, Blackwell,
\texttt{sm\_120a}) with driver 570.144, CUDA~12.8, PyTorch~2.14.0, Triton~3.8.0,
ONNX Runtime~1.30.0 and TensorRT~10.16.1.11. Timings use CUDA events after
warm-up. Parity is measured against native Triton execution of the same kernel.

\subsection{Folding plus kernels versus the alternatives}
\label{sec:folding}

This is the usefulness result. We take a two-layer block whose attention is a
custom squared-ReLU flash kernel, whose normalisations and gated activation are
custom kernels, and whose projections and residuals are standard operators. The
same block can be expressed three ways:

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{A. Folded only} --- express the attention with standard
    operators and let the compiler fold everything. This is what you get if you
    cannot ship the kernel.
    \item \textbf{B. Kernels only} --- run the custom Triton kernels but leave the
    standard layers unfused. This is the usual way to use a Triton kernel today.
    We give it two forms: eager, and \texttt{torch.compile}. The latter does not
    reimplement the kernel---since PyTorch~2.1 TorchDynamo captures a
    \texttt{@triton.jit} launch as a \texttt{triton\_kernel\_wrapper\_mutation}
    node (no graph break) and Inductor emits a call to the user's kernel---it
    fuses only the surrounding standard operators.
    \item \textbf{C. Both} --- KernelLens: the engine folds the standard layers
    and runs the kernels as plugins in one graph.
\end{itemize}

\centering
\small
\begin{tabular}{lc c}
\toprule
\textbf{Configuration} & \textbf{Latency (ms)} & \textbf{Relative} \\ \midrule

KernelLens runs the block in $7.63$~ms. That is $1.99\times$ faster than the
folded-only \texttt{torch.compile} formulation ($15.15$~ms) and $3.68\times$
faster than eager folding ($28.04$~ms), because folding has to materialise the
$O(N^2)$ attention that the custom kernel avoids. It is also $1.08\times$ faster
than the unfused Triton-kernel path ($8.24$~ms), because the engine folds the
standard layers around the kernel. The two halves are complementary: the kernel
wins where folding would materialise, and folding wins on the element-wise chain
around the projections. KernelLens is the only configuration that has both.

\subsection{Coverage: module patterns}
\label{sec:coverage}

Parity on specific operators is necessary but not sufficient: the compiler has to
handle the many ways a PyTorch module can call a Triton kernel. A conformance
suite (\texttt{tests/test\_conformance.py}) exercises fourteen patterns and
compares both backends against eager execution of the same kernels. All pass with
a maximum difference of $0.00\text{e}{+}00$:

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Two kernels in one graph}, and \textbf{the same kernel launched
    twice} with different scalars --- each launch receives its own ONNX op and
    plugin.
    \item \textbf{Multiple outputs}, including different shapes.
    \item \textbf{Dynamic host scalars}, \textbf{strided (non-contiguous)
    inputs}, and \textbf{dynamic batch sizes}.
    \item Kernels inside a \textbf{Python loop} and behind a \textbf{conditional}.
    \item Kernels that delegate to \textbf{nested \texttt{@triton.jit} helpers}.
    \item \textbf{In-place mutation} of an input buffer.
    \item A \textbf{3-D launch grid}.
    \item \textbf{fp16} and \textbf{bf16} tensors.
\end{itemize}

The one boundary is dtype coverage on ONNX Runtime: ORT~1.30 cannot bind a
bfloat16 tensor to a custom op, so bf16 models use the TensorRT backend, which
handles them exactly.

\section{Discussion and Future Work}

\subsection{When an engine wins, and when it does not}
\label{sec:enginewins}

It is worth being explicit, because the honest answer is not ``always''. On the
same RTX 5060~Ti, with \texttt{torch.compile} capturing the custom kernels
(verified: zero graph breaks, the kernels appear as
\texttt{triton\_kernel\_wrapper\_mutation} nodes):

\begin{table}[h!]
\centering
\small
\begin{tabular}{lccc}
\toprule
\textbf{Configuration} & \textbf{torch.compile} & \textbf{KernelLens TRT} & \textbf{Winner} \\ \midrule
LLaMA decoder prefill ($S{=}512$) & $7.92$ ms & $\mathbf{4.14}$ ms & TRT $1.9\times$ \\
Conv model $+$ kernel (fp32) & $\mathbf{10.40}$ ms & $11.40$ ms & compile $1.10\times$ \\
Conv model $+$ kernel (fp16) & $\mathbf{4.45}$ ms & $8.20$ ms & compile $1.84\times$ \\
Transformer block (fp32) & $7.55$ ms & $7.63$ ms & tie \\
\bottomrule
\end{tabular}
\caption{Head-to-head. TensorRT wins on GEMM-heavy transformer prefill; on
convolution-heavy graphs it is still behind.}
\label{tab:enginewins}
\end{table}

TensorRT wins on GEMM-heavy prefill, where its kernels and folding beat
Inductor's generated GEMMs. On convolution-heavy graphs it is behind, even after
two fixes made in the course of this work: the plugin now declares channel-last
formats for layout-agnostic (pointwise) kernels, so the engine no longer inserts
reformats around it, and it now enforces the dtype the kernel was compiled for,
which previously let the engine silently run fp16 models in fp32. Together these
took the fp16 convolution case from $10.86$ to $8.20$~ms with exact parity; the
remaining gap is the engine's convolution performance rather than the plugin.
\texttt{torch.compile} is a strong baseline precisely because it already fuses
and already captures Triton kernels.

The reasons to use an engine are therefore structural as much as numerical:
no Python interpreter and no \texttt{libtorch} in the serving path (no GIL, a
small footprint, deployable from non-Python services); a serialized engine that
cold-starts without recompiling; engine-level VRAM planning ($464$~MB versus
$473$/$478$~MB peak in our decoder); dynamic shapes handled by optimisation
profiles rather than recompiles and guards; and quantized inference (INT8/FP8
with calibration), where TensorRT is mature. The folding result of
\S\ref{sec:folding} is the numerical case: if you cannot ship the kernel at all,
the folded-only formulation is $2\times$ slower.

The main directions we are pursuing:

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Auto-tuning dispatch.} Fold \texttt{@triton.autotune} variants
    into one plugin with a shape-keyed C++ dispatch table.
    \item \textbf{CUDA Graphs.} Capture the zero-copy launch sequence to remove
    residual per-launch host overhead.
    \item \textbf{Distributed.} Intercept \texttt{torch.distributed} collectives
    and emit plugins with embedded NCCL communicator handles.
    \item \textbf{Hardware and platforms.} A Blackwell generator
    (cluster-launch descriptors, \texttt{cp.async.bulk}, NVFP4/MXFP6), plus
    Metal and WebGPU backends.
    \item \textbf{Safety.} SMT-based proofs that every grid access lies within
    its buffer bounds before a library is built.
\end{itemize}

\section{Conclusion}

We presented KernelLens, a compiler and runtime that turn an unmodified PyTorch
module with Triton kernels into deployable C++ plugins for ONNX Runtime and
TensorRT. One compile call and one run call per backend replace the manual
pipeline of porting kernels, writing plugin classes, building libraries and
driving each engine. Empirically, keeping a custom kernel while letting the
engine fold the rest is faster than either alone: on a block with a custom
squared-ReLU flash attention, KernelLens is $1.99\times$ faster than the
folded-only formulation and $1.08\times$ faster than the unfused kernel path,
while reproducing native Triton exactly on the research kernels.
